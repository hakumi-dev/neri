# Graph savepoint recovery

An explicit transaction can contain several graph saves. On providers declaring
`ProviderCapability.Savepoints()`, each graph save opens a savepoint after
preflight validation and before issuing writes. Successful saves remain
provisional until the outer transaction commits. A recoverable failed save
rolls back only its own writes, preserving earlier successful saves and allowing
the caller to correct the failure and retry.

SQLite implements this capability. A standalone graph save still uses its own
transaction. Providers without savepoint support retain the whole-transaction
rollback contract for graph execution failures.

## Tracker and relationship state

The context keeps two independent journals: the outer transaction checkpoint
and a checkpoint for the current graph save. The latter records entry identity,
stored baseline, state, pending write metadata, and generated-key bookkeeping.
Recovering a save restores its checkpoint without replacing the outer journal.
Keys generated by earlier successful saves remain stable; keys generated during
the failed save return to their previous temporary values.

Local scalar edits and explicit relationship intent remain retryable. Active
links propagate the restored principal key, while retired links preserve the
old database dependency as needed. Optional unlink intent remains `null` in
memory even when rollback restores the previous foreign key in the database.
A later outer rollback can still undo all successful saves and restore the
transaction's original tracker state.

## Provider API

Savepoints are owned by one active transaction lease:

```neri
provider.createSavepoint(lease)              # SavepointOpenResult
provider.rollbackToSavepoint(lease, id)      # WriteResult
provider.releaseSavepoint(lease, id)         # WriteResult
```

Creation returns `SavepointOpenResult.Created(id)` or a typed failure. Rollback
and release return `WriteResult.Saved(0)` on success. Default provider methods
return `Unsupported`. Provider wrappers that forward the capability must also
forward all three operations; `DiagnosedProvider` does so and emits completed
operation events without parameter values or native failure messages.

SQLite issues monotonically increasing positive identifiers and derives its SQL
savepoint names internally. It accepts rollback/release only for the top entry
of its owned stack and the matching lease. Rollback preserves that entry for
reuse or release. Release removes it without committing the outer transaction.
Transaction commit requires all owned savepoints to be released. Transaction
rollback and close clear the stack. Internal write-batch savepoints use a
separate name and may nest beneath the graph savepoint.

These provider operations do not expose manual savepoint management on generated
tracked contexts. Direct provider transaction control must not be mixed with a
context's private transaction journal. Contexts and providers remain sequential;
stream callbacks and diagnostic observers cannot reenter savepoint operations.

## Failure boundaries

Preflight errors and savepoint-creation failure issue no graph writes. A
recoverable execution or returned-value validation failure uses rollback-to and
release before restoring the per-save journal. The context preserves the
original write failure after successful cleanup.

SQLite constraints or triggers may abort the entire transaction. If the provider
reports that full rollback, the context restores the outer journal instead.
Failed or ambiguous cleanup blocks further writes until transaction state is
resolved; it never reports a successfully recovered save. A verified outer
rollback also discards any remaining per-save checkpoint.

## Verification and references

The SQLite provider contract checks nested ownership, stale identifiers, LIFO
rejection, retained rollback targets, commit restrictions, and close cleanup.
The generated relationship consumers check earlier successful saves, a later
constraint failure after partial graph execution, generated-key recovery,
retry and commit, later outer rollback, optional unlink/reassignment, and native
whole-transaction abort. Independent contexts verify stored row and FK values.
The diagnostic contract checks forwarding, failure classification, and
observer reentrancy. Injected rollback-to/release failures and malformed control
results verify that writes remain blocked until an explicit outer rollback,
after which generated-key graph saves can be retried.

Primary references checked on 2026-09-22:

- Microsoft, [Using transactions: savepoints](https://learn.microsoft.com/en-us/ef/core/saving/transactions#savepoints):
  saving within an existing transaction establishes a recovery point so a failed
  save can be corrected and retried while preserving earlier work.
- SQLite, [Savepoints](https://www.sqlite.org/lang_savepoint.html): rollback-to
  retains the target, release remains provisional, and outer rollback undoes
  released inner work. Neri's owned API adds strict LIFO validation.
- SQLite, [ON CONFLICT](https://www.sqlite.org/lang_conflict.html): ROLLBACK
  failures may abort the outer transaction rather than just the statement.
- C. Mohan, D. Haderle, B. Lindsay, H. Pirahesh, P. Schwarz,
  [ARIES: A Transaction Recovery Method Supporting Fine-Granularity Locking and Partial Rollbacks Using Write-Ahead Logging](https://www.cs.cmu.edu/~15849g/readings/mohan92.pdf),
  *ACM TODS* 17(1), 1992, section 5.2, p. 117. The verified section describes
  savepoints as boundaries for partial rollback. This motivates the distinction
  between local recovery and transaction rollback; Neri's in-memory tracker
  journal does not implement ARIES or database write-ahead logging.
